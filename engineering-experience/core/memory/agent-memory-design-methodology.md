## 一、先问「为什么需要记忆」，而不是「用什么存」

做 memory 之前，先别急着问是用向量库、图数据库，还是把历史对话直接塞进上下文。第一步应该先问：**这个 Agent 为什么需要记忆？**

因为 memory 的核心价值**不是让 Agent 记住所有东西，而是在长期交互里保持连续性**。这个价值判断决定了后面所有设计取舍——必要性越强，memory 做得越深；必要性不强，保持轻量即可。

---

## 二、记忆必要性的五个判断维度

一般来说，memory 的必要性可以从这五个层面来看：

| # | 维度 | 含义 |
|---|------|------|
| 1 | **体验连续** | 用户不需要每次都重新介绍自己、项目背景和当前任务 |
| 2 | **效率提升** | 已确认过的信息不需要反复提问，也不需要反复消耗 token |
| 3 | **个性化** | Agent 记住用户偏好，例如输出格式、表达风格、常用业务场景 |
| 4 | **长期任务** | 持续跟进项目、案件、客户或研究任务时，需要知道之前推进到了哪里 |
| 5 | **业务壁垒** | 持续沉淀用户上下文、业务事实和协作关系，体验会越来越贴合用户 |

> 判定口诀：**如果 Agent 记住了上次发生的事，会产生更好的结果吗？** 是 → 加记忆；任务天然无状态（批处理、一次性格式化）→ 记忆徒增复杂度而无价值。

---

## 三、记忆设计的六个环节

确定要做 memory 之后，可以拆成六个环节：

### 1. 判断信息要不要记

不是所有信息都值得进入长期记忆。用三个标准判断：**有没有长期价值、能不能被结构化、会不会影响后续的个性化体验**。同时满足才值得进 memory。

### 2. 抽取和分类

确定要记之后，不要直接存原句。更好的方式是抽成**结构化记忆**，包括：实体、关系、时间、来源、置信度和记忆类型。

记忆类型可以分成五类，这样后面检索和使用时会更稳定：

- 用户偏好
- 业务事实
- 过程结论
- 任务状态
- 程序性记忆

### 3. 暂存、去重和合并

Memory 最怕脏数据。信息在进入长期记忆前，最好先放入**暂存区**做去重、合并和更新：

- 同一类偏好可以合并
- 冲突信息要标记
- 过期信息要降权

这一步的目标是**减少重复记忆和错误记忆**。

### 4. 分层存储

Memory 不一定只放在一个地方：

| 内容 | 存放位置 |
|------|----------|
| 短期任务状态 | Session / Runtime State |
| 长期偏好和业务事实 | 长期存储 |
| 需要语义检索的内容 | 向量库 |
| 关系很强的业务 | 图结构 / 关系型数据库 |

**设计的深度取决于业务复杂程度**：普通工具型 Agent 用轻量记忆就够了；长期任务型、知识型或专业服务型 Agent，memory 需要更完整。

### 5. 检索

Memory 不是写进去就结束，关键是**何时查、查什么、查多少**。检索时要根据当前任务判断：

- 是否符合用户偏好
- 是否符合项目背景
- 是否需要历史结论和之前的任务状态

检索结果和排序要压缩，不能全部塞回上下文。这一步可以综合考虑：**相关性、时间、来源可靠性、使用频次、业务重要性**。

### 6. 动态维护

Memory 一定要能**更新、删除和总结**。因为用户偏好会变化、业务事实会过期、历史结论也可能被推翻。

一个可用的 memory 系统至少要支持五个操作：

```
add（写入）→ search（检索）→ update（更新）→ delete（删除）→ reflection（反思总结）
```

少了这些，系统会越用越脏，最后记忆反而变成噪音。

---

## 四、长期记忆 vs 短期记忆

这里要明确区分两类记忆，**不要混在一起**：

| 类型 | 服务对象 | 内容 |
|------|----------|------|
| **短期记忆** | 当前任务 | 当前步骤、已上传文件、工具调用结果、临时上下文 |
| **长期记忆** | 跨会话体验 | 用户偏好、稳定背景、长期项目、重要的业务关系 |

---

## 五、复杂度按业务需求定

最后，memory 的复杂度一定要**按业务需求来定，而不是一味追求复杂**。

先判断这个 Agent 是否满足以下任一条：

- 是否需要**跨会话连续**
- 是否需要**长期个性化**
- 是否要**跟踪长期任务状态**或处理**复杂关系**
- 是否有**隐私、权限或合规**要求

然后据此决定深度：

| 需求程度 | 做法 |
|----------|------|
| 需求很轻 | 不要上来就做复杂的记忆系统，保持轻量、可控、可维护 |
| 强依赖长期上下文 | 再考虑多层存储、关系图谱、定期 reflection、更复杂的检索策略 |

> **必要性越强，memory 做得越深；必要性不强，保持轻量即可。**

---

## 小结

Agent memory 不是把历史聊天记录全存下来，它是一套完整机制，负责：

1. **判断什么该记**
2. **决定记成什么样的结构**
3. **控制怎么存**
4. **什么时候查**
5. **持续更新和删除**

一个好的 memory 系统不追求记得多，而是追求**记得准、查得对、用得上、删得掉**。

所以做 Agent memory 设计时，顺序永远是：**先判断业务必要性 → 再决定复杂程度 → 最后按六环节落地**。
