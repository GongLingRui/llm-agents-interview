# Chain-of-Thought Prompting Elicits Reasoning in Large Language Models

## Metadata

- Authors / Year / Venue: Wei et al. · 2022 · arXiv:2201.11903
- Links: https://arxiv.org/abs/2201.11903
- Tags: reasoning-planning
- Last reviewed: 2026-10-07
- Reference: [paper-cot-2022](../../../references/papers.md#paper-cot-2022)

## TL;DR

用 few-shot 示例诱导模型写出 **中间推理步骤**，再给最终答案；提升多步算术/常识/符号任务表现。它是「显式推理痕迹」源头之一，**本身不是 Agent Planning / Tool Use**。

## Problem setup

标准 few-shot 直接答最终值时，模型在多步推理任务上脆弱；需要一种不改权重、只改提示形态的诱导方式。

## Method / Mechanism

```text
Exemplar: 问题 → 逐步推理文本 → 答案
Query:    问题 → （模型生成）逐步推理 → 答案
```

关键是示例中展示「中间计算/逻辑」，而非只给 Q→A。

## How it changes the Agent Loop

- **可选策略层**：在 Decide 前/中增加可见推理 token。
- **不改变** Act/Observe 契约；无工具时 CoT 仍可能幻觉事实。
- 与 ReAct 对比：CoT 无环境动作；ReAct = CoT 痕迹 ∩ 工具交错。

## Experiments that matter

- 足够大的模型上 CoT 收益更明显（尺度效应）；小模型可能写「假推理」。
- 工程含义：别假设「打开 CoT」对所有模型/任务都免费变强。

## Engineering takeaways

1. CoT = 提示诱导的推理痕迹，≠ 持久 Plan 状态机。
2. 生产若暴露 CoT：注意延迟、成本、隐私与用户可见性策略。
3. 需要外部事实时，用工具/RAG 锚定，不要靠更长 CoT。
4. 评测应同时看正确率与「推理-答案一致性」，防表面步骤。

## Limitations & failure modes

- 流畅错误推理（rationalization）。
- Token 成本上升；与前缀缓存/延迟预算冲突。
- 与系统硬约束冲突时，模型仍可能「推完再违规」。

## When you should / shouldn't use it

| 应该 | 不应该 |
|------|--------|
| 多步符号/算术类、需中间检查 | 当作 Memory 或安全策略 |
| 与 Verifier 组合做自我检查 | 替代 Tool Use / Eval |
