# GPTQ: Accurate Post-Training Quantization for Generative Pre-trained Transformers

## Metadata

- Authors / Year / Venue: Frantar, Ashkboos, Hoefler, Alistarh · 2022（arXiv）/ ICLR 2023（OPTQ）
- Links: https://arxiv.org/abs/2210.17323 · code: https://github.com/IST-DASLab/gptq
- Tags: model-optimization
- Last reviewed: 2026-10-07
- Reference: [paper-gptq-2022](../../../references/papers.md#paper-gptq-2022)

## TL;DR

面向生成式 Transformer 的 **训练后权重量化（PTQ）**：用近似二阶信息，按层、近似「一步定稿」地把权重压到低比特，尽量保持层输出。属于 **推理/压缩层** 杠杆，**不改变 Agent Loop 的 Decide/Act/Observe 契约**。

## Problem setup

大 GPT 级模型推理显存与带宽压力大；需要 **无需重训**、可扩展到数十亿～千亿参数的权重量化，且生成质量不能崩。

## Method / Mechanism

```text
校准数据 → 逐层估计权重对层输出误差的重要性（近似 Hessian）
         → 按列/块量化权重，并用剩余权重补偿量化误差
         → 得到低比特权重（常见工程形态：权重量化为主）
```

- **PTQ / one-shot**：训练后校准，不走完整 QAT。
- **OBS 系更新**：量化某列后，按二阶近似把误差「推」到未量化权重。
- 与「整网均匀量化」对比：按层、有补偿，低比特更稳。

## How it changes the Agent Loop

| 环节 | 影响 |
|------|------|
| Loop 控制面 | **无**：Thought/Action/Observation 协议不变 |
| 每次 LLM 调用 | 同一拓扑下换 **权重表示** → 显存/吞吐/可能的质量漂移 |
| Eval | 必须用 **工具 schema / 多步任务** 回归，不能只看困惑度 |

映射：[model-optimization](../../../runtime/model-optimization/model-optimization.md) Canonical；服务侧批与 KV 仍归 [llm-inference](../../../runtime/llm-inference/llm-inference.md)。

## Experiments that matter

- 论文在大规模 GPT/OPT 族上展示：低比特权重量化相对朴素 PTQ 基线更保生成质量；并报告端到端推理加速（**具体倍数随硬件与内核而变，勿把原文数字当你的 SLO**）。
- 工程取用：校准成本相对 QAT 低；上线前在你的域重跑 Agent 轨迹评测。

## Engineering takeaways

1. GPTQ = **权重量化 PTQ 方法族**的代表，选型时对比引擎是否支持该格式与内核。
2. 校准集应覆盖 **工具调用 / 结构化输出** 分布，避免只用通用语料。
3. Agent 验收看：任务成功率、schema 合规、安全切片——不是 MMLU 微降就放行。
4. 发布钉 **模型指纹**（基座 + 量化方案）；量化变更会使前缀缓存键失效。

## Limitations & failure modes

- 低比特常先伤 **结构化生成**（JSON / 枚举工具参数）。
- 多步轨迹上误差可累积，平均困惑度「差不多」仍可能任务翻车。
- 质量依赖校准与内核实现；论文设置 ≠ 你的线上分布。

## When you should / shouldn't use it

| 应该 | 不应该 |
|------|--------|
| 显存/成本瓶颈在大模型权重，且有 Agent 回归门禁 | 无评测就把 INT3/4 当免费午餐 |
| 权重量化路径与服务引擎已打通 | 把「换量化」当成修 Agent 规划逻辑 |
